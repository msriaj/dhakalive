# R2 media storage

Media lives in Cloudflare R2 in every environment above development. Nothing is
written to a container's disk in production — containers are replaced routinely,
and anything stored inside one is lost with it.

## Why the S3 adapter

R2 speaks the S3 API, so `@payloadcms/storage-s3` is the adapter. Two settings
are non-obvious and both are required:

| Setting          | Value  | Reason                                                            |
| ---------------- | ------ | ----------------------------------------------------------------- |
| `region`         | `auto` | R2 has no regions, but the S3 client refuses to sign without one. |
| `forcePathStyle` | `true` | R2 does not support virtual-host-style bucket addressing.         |

Both are surfaced as environment variables, so nothing is hard-coded:

```
CLOUDFLARE_R2_REGION=auto
CLOUDFLARE_R2_FORCE_PATH_STYLE=true
```

## The `prefix` trap

The storage plugin is attached in **every** environment and switched with
`enabled`, and the plugin's `prefix` option is deliberately **not used**.

Setting `prefix` makes the plugin contribute a `prefix` column to the media
collection — but only while the plugin is enabled. Migrations are generated by
whichever developer runs the command, so a developer without R2 credentials
would produce migrations missing a column production needs, and uploads there
would fail with:

```
column media.prefix does not exist
```

That is not hypothetical; it is what happened before this was fixed. The bucket
holds nothing but media, so a prefix bought nothing. Configuration varies by
environment; **the schema must not**.

Verify after any storage change:

```bash
pnpm --filter @dhakalive/web migrate:create schema_check
```

With and without R2 credentials set, it must report _no schema changes_.

## Bucket setup

1. Create a bucket, e.g. `dhakalive-media`.
2. Create an R2 API token with **Object Read & Write**, scoped to that bucket.
3. Attach a custom domain (`media.example.com`) in the bucket's settings. This
   is what makes objects public and puts them behind the CDN — the bytes never
   transit the application.
4. Set `CLOUDFLARE_MEDIA_PUBLIC_URL=https://media.example.com`.

Use separate buckets per environment. A staging deploy writing into the
production bucket is a content incident, not a config mistake.

## Filling in the configuration

The Cloudflare MCP connector exposes R2, D1, KV and Workers — but **no zone,
DNS, cache-rule or token endpoints**. So the bucket can be inspected and created
through it; credentials and CDN settings cannot. Secrets are issued by the
dashboard by design.

| Variable                          | Source                                                             | Connector? |
| --------------------------------- | ------------------------------------------------------------------ | ---------- |
| `CLOUDFLARE_R2_BUCKET`            | Bucket name                                                        | yes        |
| `CLOUDFLARE_R2_REGION`            | Always `auto`                                                      | n/a        |
| `CLOUDFLARE_R2_FORCE_PATH_STYLE`  | Always `true`                                                      | n/a        |
| `CLOUDFLARE_ACCOUNT_ID`           | R2 → Overview, or the dashboard URL after `/accounts/`             | no         |
| `CLOUDFLARE_R2_ENDPOINT`          | `https://<account-id>.r2.cloudflarestorage.com`                    | no         |
| `CLOUDFLARE_R2_ACCESS_KEY_ID`     | R2 → API → Create API token → **Object Read & Write**              | no         |
| `CLOUDFLARE_R2_SECRET_ACCESS_KEY` | Shown once when the token is created                               | no         |
| `CLOUDFLARE_MEDIA_PUBLIC_URL`     | Custom domain bound to the bucket, or its `r2.dev` URL for testing | no         |
| `CLOUDFLARE_ZONE_ID`              | Zone → Overview (needs a domain on the account)                    | no         |
| `CLOUDFLARE_API_TOKEN`            | My Profile → API Tokens → `Zone → Cache Purge`, this zone only     | no         |

Put them in `.env` — it is gitignored, and secrets must never be pasted into a
chat transcript or committed.

Then prove it actually works, rather than assuming:

```bash
pnpm verify:r2
```

It heads the bucket, writes an object, reads it back, compares bytes, checks
public delivery and cleans up. A wrong endpoint or a read-only token is
otherwise invisible until the first editor upload fails.

A newly added custom domain sits in **Initializing** while Cloudflare creates
the DNS record and issues the certificate. During that window — and for a while
afterwards, if the host was queried before it existed — a machine can hold a
negative DNS cache while the domain is already serving. The public-delivery
check reports `ENOTFOUND` in that case. Confirm which it is:

```bash
dig +short media.dhakalive.com
curl -I --resolve media.dhakalive.com:443:<one-of-those-ips> https://media.dhakalive.com/x
```

A `404` there means the bucket is wired correctly and only the local resolver is
behind. The other four checks are what actually prove the configuration.

## CORS

Only needed if the browser fetches objects directly with scripted requests.
Plain `<img>` and `<video>` do not require CORS. Direct-to-R2 uploads from the
admin panel would.

```json
[
  {
    "AllowedOrigins": ["https://example.com", "https://cms.example.com"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["Content-Length", "Content-Type", "ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

Never use `"AllowedOrigins": ["*"]` with write methods.

## Image delivery

`next/image` refuses hosts not listed in `remotePatterns`, returning 400. Two
hosts are allowed: the R2 custom domain and the site's own origin.

Self-hosted media — development, or any environment before R2 is wired — is
served by Payload from the app's own origin as an _absolute_ URL, which the
optimiser treats as remote. `MediaImage` rewrites those to a relative path,
matched on Payload's `/api/<collection>/file/` route. R2 URLs live on a different
host and stay absolute.

## Uploads

| Control          | Behaviour                                                               |
| ---------------- | ----------------------------------------------------------------------- |
| MIME allowlist   | Server-side. `text/html`, `image/svg+xml` and executables are refused.  |
| Size limit       | 50 MB, enforced at the transport **and** in a hook                      |
| EXIF             | Stripped by sharp on resize — camera GPS can expose a source's location |
| Alt text         | Required for images, and before use as a featured image                 |
| Responsive sizes | thumbnail, card, feature, wide, og (1200×630)                           |

The hook check exists because the transport limit only covers HTTP; imports,
seeds and migrations would otherwise be unguarded.

## Local development

R2 is not required locally — uploads fall back to disk. To exercise the real
storage path, run MinIO, which speaks the same S3 API:

```bash
docker compose --profile storage up -d minio minio-init
```

Then point the adapter at it:

```
CLOUDFLARE_R2_BUCKET=dhakalive-media-dev
CLOUDFLARE_R2_ACCESS_KEY_ID=dhakalive
CLOUDFLARE_R2_SECRET_ACCESS_KEY=dhakalive-dev-secret
CLOUDFLARE_R2_ENDPOINT=http://127.0.0.1:9000
CLOUDFLARE_MEDIA_PUBLIC_URL=http://127.0.0.1:9000/dhakalive-media-dev
```

Uploads then land in the bucket and are served from the "media domain", exactly
as in production. The MinIO console is at http://localhost:9001.

These credentials are development-only and are published here deliberately —
they grant access to a throwaway container and nothing else.
